# KZG与IPA的取舍

> **支撑** ｜ 前置：02_承诺与哈希/02_承诺方案/04_可信设置与SRS

**一句话**：IPA 不需要可信设置但 proof 随电路规模对数增长；KZG proof 恒定但要 SRS。v23 已删掉 IPA。

**打个比方**：IPA 像「每次验算都重新推导」，不需要预制模具，但证明越算越长；KZG 像「用预制模具压一下」，快而短，但要有人造模具。

**在 EZKL 里的落点**：v23 的破坏性变更。

## 一、两条技术路线

多项式承诺有两大流派：

| | KZG | IPA（内积论证） |
|---|---|---|
| 数学基础 | 椭圆曲线配对 | 离散对数 + 内积 |
| 需要可信设置 | **要**（SRS） | **不要** |
| 证明大小 | 恒定（33 字节） | O(log n) 个群元素 |
| 验证时间 | 常数（2 次配对） | O(n) 或 O(log n)（取决于变体） |
| 后量子 | 否 | 否 |

**核心交换**：KZG 用「一次性的信任」换「恒定大小 + 常数验证」；IPA 用「更大的证明 + 更慢的验证」换「不需要信任」。

## 二、Halo2 原设计为什么选 IPA

Halo2（Zcash 的 halo2，2020）最初用 IPA，有两个原因：

**原因一：不想有可信设置。**
Zcash 的团队对可信设置很警惕（历史上出过问题）。用 IPA 就完全绕开这个假设。

**原因二：递归友好。**
IPA 的验证电路比 KZG 的配对电路小得多。要在电路里验另一个证明（递归），IPA 更划算。

所以「Halo2 + IPA」曾经是一个「无信任 + 可递归」的组合。

## 三、那为什么 v23 删了 IPA

三个现实原因：

**原因一：证明太大。**
IPA 的 proof 是 O(log n) 个群元素。n = 65536 时约 16 个点，每个 33 字节 → 500+ 字节，是 KZG 的 15 倍。链上验证时 gas 差很多。

**原因二：验证太慢。**
IPA 验证要做 O(n) 次群运算（或用 Bulletproofs 技巧降到 O(log n)，但实现复杂）。在「1 秒验证」的场景里不可接受。

**原因三：生态绑死 BN254。**
既然已经为了 EVM 兼容选了 BN254（有配对），那 KZG 就是顺理成章的选择。IPA 的优势（无信任）被「反正要用配对」抵消了。

**于是 v23 干脆只留 KZG。**

## 四、这对你意味着什么

| 影响 | 具体 |
|---|---|
| 必须接受可信设置 | SRS 必须来自可信仪式（`06/03/01`） |
| 证明小、验证快 | 19 KB、纯验证约 3 ms，对 1 秒指标很宽松 |
| 无法递归 | aggregation circuit 也一起删了（`04/02/04`） |
| 换曲线成本极高 | 整条工具链都绑在 BN254 + KZG |

**一句话**：v23 用「信任」换「性能」，而且换得很彻底。

## 五、如果以后要免信任怎么办

三条路，都要动大手术：

1. **换回 IPA**：需要找回 v22 的代码，或者自己接 halo2 的 IPA 后端；
2. **换 STARK**：完全不同的证明系统，proof 大一个数量级，但无信任、后量子；
3. **用递归的 STARK 包一层**：把 KZG 证明「翻译」成 STARK 证明，成本极高。

现实中没人这么做，因为「可信设置」在实践中是可接受的（以太坊自己就用 KZG）。

## 六、自检答案

> 问：说清「EZKL 为什么只要 KZG」，以及这个选择的信任代价。

答：因为生态已经绑在 BN254（为了 EVM 兼容），而 BN254 支持配对，KZG 就是最自然的选择；同时 KZG 的 proof 恒定 33 字节、验证只要两次配对，对「1 秒验证」指标最有利，而 IPA 的 proof 大 15 倍、验证慢一个数量级。信任代价是必须接受一次性可信设置（SRS），并且失去了「无信任」和「递归友好」这两个原本属于 Halo2 的优势。

## 七、一句话记住

**IPA 免信任但笨重，KZG 轻快但要信一次。v23 选了轻快，从此背上 SRS。**
