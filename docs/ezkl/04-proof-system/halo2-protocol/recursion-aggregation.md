# 递归与聚合证明

> **选读** ｜ 前置：04_证明系统/02_Halo2协议/01_证明生成全流程

**一句话**：大电路拆小、各自出证明、再递归合成一个。听起来能救大模型，但 v23 已经删掉 aggregation circuit。

**打个比方**：把 100 份作业分别批完，再写一张「这 100 份都合格」的总结，最后只验这张总结。难点是：总结本身也要能被验证。

**在 EZKL 里的落点**：缺失（v23 移除）；这是缺口，不是现成功能。

## 一、两个概念，容易混

| | 递归证明（recursion） | 聚合证明（aggregation） |
|---|---|---|
| 做什么 | 在电路里**验证另一个证明** | 把 N 个证明合成 1 个 |
| 输出 | 一个「证明的证明」 | 一个「代表 N 个陈述的证明」 |
| 关系 | 是聚合的手段 | 是递归的用途之一 |

递归是底层能力，聚合是上层应用。有了递归，聚合就好做。

## 二、递归怎么工作

普通证明：证明「我知道 w 使 C(x,w)=y」。

递归证明：证明「**存在一个证明 π，使得 verify(vk, π, x, y) = true**」。

也就是说，把「验证算法」本身写成了电路。

于是：

- 内层电路可能很大（几百万行）；
- 外层电路只要装「验证逻辑」（几万行）；
- 你可以一层层往上套。

**这就是「把大电路拆小」的理论基础**（`04/02/04` 的「大模型切分」）。

## 三、代价

递归不是免费的：

| 项 | 成本 |
|---|---|
| 验证电路 | 配对运算要进电路，非常贵（几万行） |
| 曲线切换 | 内外层常用不同曲线（避免「同曲线递归」的循环依赖） |
| 工程复杂度 | 极高，需要专门的递归框架 |

**最贵的是「配对进电路」**：一次配对在电路里要几万条约束，而 KZG 验证要两次配对。

这就是为什么 IPA 曾经更适合递归（不需要配对），也是 v23 删 IPA 后递归更难的深层原因。

## 四、EZKL v23 的现状

事实：**aggregation circuit 被删了。**

意味着：

- 不能把多个证明合成一个；
- 大模型切分后，你只能得到 N 个独立证明；
- 验证方要逐个验（N 次 verify）。

后果很直接：

- N = 10，验证 10 × 50 ms = 500 ms，勉强；
- N = 100，5 秒，指标崩。

## 五、自己实现要多少工作量

如果要补上，需要：

1. 一个能装「KZG 验证」的电路（用 halo2 写，约几万行约束）；
2. 曲线切换（内层 BN254，外层可能要另一条曲线）；
3. 递归的 setup 与 SRS 管理；
4. 与现有 prove 流程的对接。

**量级：几个人月，且需要深度 zk 工程经验。** 这不是一个「加个依赖」能解决的事。

## 六、所以对你项目的结论

如果你的方案里写「大模型切分 + 递归聚合」，要非常小心：

- 理论上成立；
- 但 EZKL v23 没有现成实现；
- 自己做的成本远超一个毕设/项目的范围。

**更现实的路**：

- 控制模型规模，让 k ≤ 26（公开 SRS 上限）；
- 或者接受「N 个证明 + 批量验证」（并行验，摊薄时间）；
- 或者把「切分」放在应用层（多个模型分别证明），而不是电路层。

## 七、自检答案

> 问：说清「递归能解决什么、代价是什么」，以及为什么它救不了 ResNet50。

答：递归能把「验证一个证明」写成电路，从而把多个证明合成一个、或把大电路拆成多层小电路，解决「单电路装不下」的问题。代价是验证电路本身很贵（配对要几万条约束）、需要曲线切换和专门的递归框架、工程复杂度极高。救不了 ResNet50 是因为：单段电路仍需装下至少一个 block（约 1 亿行、k=27），已超公开 SRS 上限；且 v23 删了聚合电路，没有现成实现。

## 八、一句话记住

**递归是「证明的证明」。理论上能拆大模型，实际上 EZKL 没这个能力，自己做要几个人月。**
