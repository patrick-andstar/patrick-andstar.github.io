# 可靠性误差与安全参数

## 一、误差不是一个数，是一堆小概率相加

一个 Halo2 证明里，至少五处依赖随机性：

| 来源 | 单次失败概率 |
|---|---|
| Schwartz-Zippel 抽查（`01/04/03`） | d / \|F\| |
| 置换论证的 grand product | 约 n / \|F\| |
| 查找论证（LogUp） | 约 n / \|F\| |
| 多开点随机系数（`04/02/02`） | 1 / \|F\| |
| Fiat-Shamir 的哈希碰撞 | 约 q² / 2^256 |

（d 是多项式次数，n 是行数，q 是查询次数。）

总误差用**联合界**（union bound）加起来：几项相加，仍然远小于 2⁻¹⁰⁰。

## 二、算一遍

BN254 的标量域 |F| ≈ 2²⁵⁴，n = 2¹⁶：

- SZ：2¹⁶ / 2²⁵⁴ = 2⁻²³⁸
- 置换：2¹⁶ / 2²⁵⁴ = 2⁻²³⁸
- 查找：同量级
- 多开点：2⁻²⁵⁴
- FS：q² / 2²⁵⁶，q 小的时候可忽略

加起来还是 2⁻²³⁷ 量级。**远远超过 100 bit 的要求。**

所以 EZKL 的安全性瓶颈不在这些概率项，而在别处（见下）。

## 三、真正的瓶颈：100 bit 的曲线

BN254 的离散对数安全约 100 bit（`01/03/04`）。

也就是说：即使所有概率项都小到 2⁻²³⁷，攻击者仍可以用 **2¹⁰⁰ 次运算**去破解底层曲线。

**所以系统的安全等级 = min(概率项, 曲线安全) = 约 100 bit。**

这就是为什么我反复强调「254 位域 ≠ 254 位安全」。写报告时，正确的安全参数是 100 bit，不是 128，也不是 254。

## 四、80 bit 为什么不够

历史上 80 bit 被认为是够的（2010 年前）。现在不够，原因有两个：

1. **算力增长**：2⁸⁰ 次运算从「不可能」变成「国家级项目可行」；
2. **算法进步**：数域筛法的常数项一直在优化。

NIST 现在的建议：112 bit 起步，128 bit 主流，2030 年后可能提到 128+。

**100 bit 落在「可接受但不宽裕」的区间。** 这是 BN254 的历史包袱，不是 EZKL 的选择。

## 五、工程上怎么处理

三条：

**第一，写清口径。**
「约 100 bit，与主流 zkEVM 同档」比「128 bit 安全」诚实得多。

**第二，别自己降参数。**
有些人为了省行数，把 `logrows` 或域参数调小 —— 那会真的降低安全等级。默认值是有理由的。

**第三，区分「概率项」和「计算项」。**
概率项（抽查失败）可以靠重试/加轮数降低；计算项（离散对数）不能，只能换曲线。

## 六、一个容易忽略的点

**可靠性误差是「单次」的。**

如果你允许攻击者提交 10⁶ 个假证明，那总成功概率是 10⁶ × 2⁻¹⁰⁰ ≈ 2⁻⁸⁰ —— 掉了 20 bit。

所以高并发场景（比如公开的验证服务）要考虑「查询次数」这个因子。这也是为什么 Fiat-Shamir 那一行的误差里有个 q²。

## 七、自检答案

> 问：说清「为什么 80 bit 在今天不够用」。

答：因为 80 bit 意味着攻击者只需约 2⁸⁰ 次运算，而这个量级在今天的分布式算力下已从「不可能」变成「国家级项目可完成」；同时数域筛法等算法的常数项持续优化，实际难度还在下降。NIST 目前的建议是 112 bit 起步、128 bit 主流，所以 80 bit 已低于工程底线。

## 八、一句话记住

**概率项小到 2⁻²³⁷，但曲线只值 100 bit。系统的安全 = 最弱那一环。**
