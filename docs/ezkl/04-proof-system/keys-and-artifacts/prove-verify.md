## 一、两边的输入输出（已按 v23 实测校正）

| | 输入 | 输出 | 本项目实测 |
|---|---|---|---|
| `prove` | `witness.json` + `model.compiled` + `pk.key` + `kzg16.srs` | `proof.json`（19 KB） | 2.9–4.2 s |
| `verify` | `proof.json` + `vk.key` + `settings.json` + `kzg16.srs` | `true/false` | 端到端 67–78 ms；**纯验证约 3 ms** |

两处容易记错，先纠正：

1. **`prove` 不是只要 witness 和 pk。** 它还要 `model.compiled`（`-M`）——因为要按电路结构把 witness 填进表格。
2. **`verify` 不是只要 vk 和 proof。** 它还要 `settings.json`（`-S`，描述电路参数）和 **SRS**（`--srs-path`）。halo2 的 KZG 验证接口需要 `ParamsVerifier`，配对运算不是只用 vk 就能做的。

它确实不碰的东西是：`pk.key`、`witness.json`、`model.onnx`。

## 二、verify 内部做了什么

四步，全是常数时间：

1. **绑定公开输入**：把 instances 插值成多项式、算出承诺，作为 `common` 写进 transcript。后面所有挑战都依赖它，所以改公开输入必然导致挑战对不上（这一步常常是漏洞来源）；
2. **重算挑战**：按顺序读 proof 里的承诺，挤 theta → beta → gamma → y → x（`02/01/04`）；
3. **验约束恒等式**：在 x 点检查门约束、置换、查找的合并等式，以及 `h(x)·Z_H(x)` 是否成立。这一步是纯域运算，很快；
4. **验打开**：multiopen 把一堆开值合并成两个承诺 `q_x`、`q_ωx`，再做两次配对完成 KZG 校验（`02/02/03`）。

没有一步与电路行数有关。所以 65536 行和 65536×16 行的电路，`verify` 的计算部分几乎一样。

## 三、那 70 毫秒花在哪：一个容易读错日志的坑

先说结论：本项目三次实测（同一份 k=16 的 proof）：

> 端到端 78 / 77 / 67 ms
> 日志自报 `verify took 0.3`

那个 **`0.3` 不是 0.3 秒，是 0 秒 + 3 毫秒**。

因为日志格式是 `{}.{}`（整秒 + 毫秒），毫秒部分不补零：3 ms 打印成 `0.3`，300 ms 会打印成 `0.300`，30 ms 打印成 `0.30`。看到 `0.3` 就当成 0.3 秒，会把验证时间高估 100 倍 —— 这是本项目早期笔记里踩过的坑，我在这里改正。

所以 70 毫秒的构成是：

| 项 | 量级 |
|---|---|
| 启动 33 MB 二进制 + 初始化运行时 | 几十毫秒 |
| 读 132 KB `vk.key` 并反序列化（曲线点解码） | 几毫秒 |
| 读 8.4 MB `kzg16.srs`（**最大的一块 IO**） | 十几毫秒 |
| **纯验证（重算挑战 + 多开点校验 + 2 次配对）** | **约 3 ms** |

**密码学只占 5%。** 剩下全是「启动 + 读文件」。

这也解释了一个实践结论：**如果指标是「验证 ≤ 1 秒」，命令行本来就够用；要拼吞吐，才需要常驻服务**（`06/01/02`）。

## 四、verify 会失败在哪几种情况

| 现象 | 可能原因 |
|---|---|
| 约束不满足 | witness 或 instances 被改过 |
| 点解码失败 | `proof.json` 里的字节不是合法曲线点 |
| 挑战对不上 | 序列化顺序/字节序不一致（版本不匹配） |
| vk 不匹配 | 用了另一个电路的 vk |

**排查顺序**：先看是不是改过文件，再看版本，最后才怀疑密码学。实践中前三类占九成。

## 五、一个容易忽略的成本：instances 的大小

`verify` 的计算量虽然与电路行数无关，但**与公开输入的数量有关**。

因为 instances 要参与群运算（把它们绑定进电路），数量一多就要做 MSM。100 万个公开输入 → 100 万次标量乘 → 验证时间线性增长。

这也是为什么 `proof.json` 会从几 KB 涨到几百 KB：**它里面装的主要不是证明，是公开输入**。本项目 `proof.json` 18.8 KB，其中真正的证明字节块只有 3,072 字节，其余是 instances 的十六进制串。

这就是「公开输入必须承诺化」的动机（`05/04/03`）：把一百万个值压成一个 Poseidon 哈希，验证就回到常数时间。

## 六、自检答案

> 问：说清「验证为什么是常数时间」，以及它到底验了哪几件事。

答：因为验证只做常数次群运算和配对：重算挑战、检查多开点等式、检查 instances 绑定、做两次配对，全部与电路行数无关（只与公开输入的个数有关）。它验的是：这份证明确实对应这个 vk（即这个电路），其中的承诺满足 KZG 打开关系，公开输入被正确绑定，且所有约束在随机点上成立。

## 七、一句话记住

**prove 花几秒把电路压成一个点；verify 花三毫秒把这个点验一次，剩下 70 毫秒都在启动和读 SRS。**
