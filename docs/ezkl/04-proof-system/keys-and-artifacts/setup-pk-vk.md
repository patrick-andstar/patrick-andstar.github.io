# setup与pk-vk

> **核心** ｜ 前置：04_证明系统/02_Halo2协议/01_证明生成全流程

**一句话**：pk 是证明者的密钥（几百 MB），vk 是验证者的密钥（百来 KB）；两者都从电路 + SRS 生成。

**打个比方**：pk 是厨师的全套刀具，很大但只有厨房用；vk 是食客手里的一把验菜尺，很小但谁都能拿。

**在 EZKL 里的落点**：src/pfsys/srs.rs；setup 命令；pk.key / vk.key。

!!! question "自检（能答上来就算过）"
    说清「为什么 pk 那么大而 vk 那么小」。

---

> 读完约 8 分钟。这一篇解释 EZKL 里最刺眼的那个数字差。

## 一、setup 在干什么

输入：`model.compiled` + `kzg16.srs`
输出：`pk.key`（265 MB）、`vk.key`（132 KB）

它做的事：**把「电路」和「SRS」结合，预先把所有能预先算的东西都算好。**

- 证明者需要的东西 → 打进 pk；
- 验证者需要的东西 → 打进 vk。

## 二、pk 为什么这么大

因为证明者要做的活太多了，而其中绝大部分**与这次输入无关**：

| 内容 | 为什么在 pk 里 |
|---|---|
| 每个 fixed 列多项式的承诺 | 每次证明都要用，但值不变 |
| 置换论证的 σ 多项式（已承诺） | 同上 |
| 查找表的编码结果 | 同上 |
| 拉格朗日基的预计算 | 用于快速插值 |
| 各种「门系数」的展开 | 由选择子决定，编译后就固定 |

这些都是「电路级」的常量。setup 一次算完，证明时直接读。

265 MB ÷ 4.3 KB/行 ≈ 61600 行 —— 和 2¹⁶ = 65536 对得上。**pk 的大小基本就是行数的线性函数。**

## 三、vk 为什么这么小

因为验证者只做几件事：

1. 重算挑战；
2. 检查几个承诺之间的一次配对关系；
3. 检查 instances 是否被正确绑定。

他需要的东西只有：

- 几个 G1 点（承诺相关）
- 几个 G2 点（配对用）
- 电路的「指纹」（哪些多项式、多少行、哪些公开输入）

**132 KB 主要是若干个曲线点的编码**：对固定列的承诺（每个 32 字节）、配对用的 G2 点（每个 128 字节），加上字段名与版本信息。真正参与配对的只有两三个点，其余都是「这个电路长什么样」的指纹。

## 四、为什么这个不对称是必然的

这是所有「证明系统」的共同结构：

> **证明是一次性重活，验证是轻活。**

- 证明者要把 65536 行的约束全部展开、承诺、求商、开点；
- 验证者只看几个点和一个配对等式。

pk 和 vk 的大小差，就是这个不对称的物理体现。它不是 EZKL 的实现缺陷，是设计目标。

## 五、setup 的耗时与可复用性

本项目实测：4.3–4.9 秒（k=16）。

可复用条件：**电路不变 + SRS 不变**。满足这两条，`pk` 和 `vk` 可以反复用，不用重跑。

反过来：

- 改模型 → 电路变 → 重跑；
- 换更大的 SRS（因为 logrows 变大）→ 重跑；
- 换 EZKL 大版本（序列化格式可能变）→ 建议重跑。

## 六、一个常见误解

「pk 这么大，是不是包含了模型权重？」

**不一定。** 取决于 `param_visibility`：

- `fixed`：权重在 fixed 列里，pk 包含它们的承诺 —— 此时 pk 确实和权重有关；
- `private`：权重走 witness，pk 只包含结构 —— 此时换一版权重，pk 还能用。

所以「pk 265 MB」这个数字，在不同配置下含义不同。写报告时要说清是哪种。

## 七、自检答案

> 问：说清「为什么 pk 那么大而 vk 那么小」。

答：pk 里装的是证明者需要的全部预计算材料：每个 fixed 列多项式的承诺、置换 σ 多项式、查找表编码、拉格朗日基等，这些都与行数成正比，所以体积随 2^k 线性增长。vk 里只装验证者需要的东西：几个 G1/G2 点和一个电路摘要，与行数基本无关。这个不对称源于「证明重、验证轻」的根本设计。

## 八、一句话记住

**pk 是厨师的整套刀具（265 MB），vk 是食客的一把验菜尺（132 KB）。**
