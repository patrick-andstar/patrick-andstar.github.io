## 一、事实

EZKL 仓库根目录**没有 LICENSE 文件**。GitHub 上的 license 字段是空的。

仓库里只有 `cla.md`（Contributor License Agreement，贡献者协议）。

## 二、法律上这意味着什么

按著作权法默认规则：

> **没有许可证 = 保留所有权利（All rights reserved）。**

也就是说，严格讲，你没有获得「复制、修改、分发、商用」的授权。开源 ≠ 免费商用，**公开可见的代码不等于可以随便用**。

这和「MIT/Apache-2.0」是两种完全不同的状态：

| | 有 LICENSE（如 Apache-2.0） | 无 LICENSE |
|---|---|---|
| 可以使用 | 明确授权 | 法律上未授权 |
| 可以商用 | 通常可以（看条款） | 需另行获得许可 |
| 可以修改分发 | 通常可以（保留声明） | 需另行获得许可 |

## 三、CLA 是什么，不是什么

`cla.md` 是**贡献者**签的协议：你给这个项目提交代码，得同意把你的贡献授权给项目方。

它**不是**给使用者的许可。看到 CLA 就以为「可以随便用」，是常见误解。

## 四、实践上怎么办

三条路，从轻到重：

**路线一：学术/研究用途**
大多数情况没人追究，但严格说仍未获授权。写论文引用没问题（引用是合理使用），把代码打包进交付物就有风险。

**路线二：联系作者要授权**
项目背后是 Zkonduit（一家公司）。商用或交付给甲方前，发邮件问清楚授权条款，是最稳的做法。

**路线三：换实现**
如果授权谈不下来，考虑：

- 自己基于 halo2 重写（工作量大，但 halo2 本身是 MIT/Apache）；
- 换其他有明确许可证的 zkML 方案。

## 五、为什么这件事必须写进方案

因为你的交付物是「原型系统」，甲方会问：「这套东西我们能自己部署吗？」

如果答不上来许可证，整个交付就有法律风险。**这不是技术问题，但会让技术方案作废。**

建议在方案的风险章节里单列一条：

> EZKL 仓库未声明开源许可证，默认保留所有权利。商用交付前需与版权方（Zkonduit）确认授权范围；备选方案为基于 halo2（MIT/Apache-2.0）自研电路层。

## 六、一个容易搞混的点

「GitHub 上能 clone」不等于「能商用」。

- clone 是公开可访问，不是授权；
- fork 也一样；
- 只有 LICENSE 文件里的条款才是授权。

这条在国内项目里经常被忽略，直到甲方合规审查时才爆出来。

## 七、自检答案

> 问：说清「没有 LICENSE 默认意味着什么」，以及写进合同前该做什么。

答：默认是「保留所有权利」，即未授予你复制、修改、分发、商用的许可；公开可见不等于授权，CLA 只是贡献者协议而非使用者许可。写进合同前应与版权方确认授权范围（用途、部署方式、是否可再分发），或改用许可证明确（如 MIT/Apache-2.0）的替代实现。

## 八、一句话记住

**没有 LICENSE 就是「保留所有权利」。能 clone 不等于能商用，CLA 不等于授权。**
