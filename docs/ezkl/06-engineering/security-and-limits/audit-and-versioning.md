## 一、审计：v21 过了，不等于 v23 也过

EZKL v21.0.0 通过了 Trail of Bits 的审计。这是它能被工业和学术引用的重要原因。

但要注意两件事：

1. **审计的是 v21 的代码**，不是 v23；
2. 审计报告评估的是当时的威胁模型（三个性质 + 实现层面的漏洞），不是「所有场景都安全」。

v23 做了破坏性改动（见下），这些改动**没有经过同等强度的公开审计**。所以引用「已审计」时，要说清版本。

## 二、v23 删了什么（已逐项核对代码）

| 删除项 | 影响 | 核对结果 |
|---|---|---|
| IPA（内积论证） | 只剩 KZG，必须可信设置 | ✅ `src/` 里搜不到 IPA 相关代码 |
| **aggregation circuit（聚合电路）** | 大模型切分后无法递归合成（`04/02/04`） | ✅ `src/` 里搜不到 `aggregat*` |
| JS/WASM 绑定 | 浏览器端跑不了 | ✅ `src/bindings` 只剩 `python.rs`，没有 `#[wasm_bindgen]` |

**一条我原来写错、现在改掉**：**iOS 并没有被移除**。`Cargo.toml` 里仍有 `ios-metal` / `macos-metal` 两个 feature，`src/tensor/metal/` 里也还有 Metal 的 shader 与 `.metallib`。所以准确说法是「iOS 的独立绑定层不在一等支持里，但 Metal 后端能力仍在」，不能写成「移动端跑不了」。

前两条影响最大：

- 没有 IPA → 想免可信设置，只能换整套证明系统；
- 没有聚合 → 大模型切分只能出 N 个独立证明，不能合成一个。

## 三、README 与代码不一致

这是本项目核实过的具体事实：

**README 仍然写着「可以在浏览器里验证」**，但 v23 已经删掉了 WASM 绑定。

后果：

- 你按 README 去试，会发现根本没有 `ezkl.js` 或 wasm 包；
- 如果你在方案里写「支持浏览器端验证」，评审一跑就露馅。

**教训**：这类开源项目，文档滞后半年是常态。**以代码和 release note 为准，不以 README 为准。**

## 四、这给你的三条实践建议

**第一，锁版本。**
写进 `requirements.txt` 或 Cargo.lock。别用 `latest`，因为下个小版本可能删掉你在用的功能。

**第二，交叉核对。**
README 说的功能，去 `src/commands.rs` 里找对应命令；找不到就是没有。

**第三，记录你所用的版本。**
报告里写「基于 EZKL v23.0.5」，而不是「基于 EZKL」。版本漂移会让复现失败。

## 五、一个具体的复现陷阱

v23 的 `settings.json` 里有 `version` 字段。

如果你用 v23 生成 settings，再用 v22 的二进制去 compile，可能出现：

- 字段不认识 → 报错；
- 或者更糟：能读，但语义不同 → 生成出错误的电路。

所以 **settings 和二进制必须同版本**。跨版本迁移时，重新跑 `gen-settings`。
