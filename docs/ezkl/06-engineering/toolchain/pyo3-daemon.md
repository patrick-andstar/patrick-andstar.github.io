## 一、pyo3 是什么

它让 Rust 代码能被 Python 直接 `import`。

EZKL 用 pyo3 把整个库包装成 Python 包，所以你可以：

```python
import ezkl
ezkl.verify("settings.json", "proof.json", "vk.key", "kzg16.srs")
```

底层跑的还是同一份 Rust 代码，**没有跨进程开销**。

## 二、两种调用方式差多少（已实测校正）

| 方式 | 端到端耗时 | 其中纯验证 |
|---|---|---|
| CLI（`ezkl verify ...`） | **67–78 ms**（三次实测） | **约 3 ms** |
| Python 进程内（`ezkl.verify`） | 理论上是「省掉启动与读盘」的时间 | 同样约 3 ms |

注意这里的数字比早期笔记小一个数量级：早期把日志里的 `verify took 0.3` 读成了 0.3 秒，其实那是 **0 秒 + 3 毫秒**（毫秒位不补零）。`04/03/04` 有详细解释。

所以 70 毫秒里：

- 启动 33 MB 二进制（动态链接、初始化运行时）；
- 读 `vk.key`（132 KB）并反序列化（曲线点解码，比想象中慢）；
- 读 `kzg16.srs`（8.4 MB，最大的一块 IO）；
- 解析命令行、初始化日志。

**密码学只占 5%。**

> 备注：本项目环境未安装 Python 绑定（`import ezkl` 失败），所以「进程内能省多少」只有原理判断，没有实测数字。按上表的构成估算，省掉的主要是启动 + 读 SRS，量级在几十毫秒。

## 三、那还要不要做常驻服务

如果指标是「单次验证 ≤ 1 秒」，**CLI 本来就达标**（70 ms，留了十几倍余量）。

但如果指标是「每秒处理 N 个请求」，CLI 就吃亏了：每个请求都要付一次 60 多毫秒的启动与读盘成本。

常驻服务的做法：

1. 启动时加载一次 `vk.key` + `kzg.srs`；
2. 之后每个请求只做「验证」这一步（约 3 ms）；
3. 用线程池处理并发。

这样单核 QPS 从约 14（1/0.07）提到 300 量级（1/0.003，扣除调度开销后更低）。**这才是常驻服务的真实收益：不是「达标」，是「吞吐」**。

## 四、代价

| 项 | 说明 |
|---|---|
| 内存常驻 | vk 132 KB + srs（如果加载）8 MB，可以接受 |
| 状态管理 | 多租户场景要隔离（不同 vk 对应不同模型） |
| 升级 | 换模型要重载 vk，需要热更新机制 |
| 安全 | 常驻进程持有 vk，要做好权限隔离 |

## 五、在 EZKL 里

- `src/bindings/` 是 pyo3 的包装层；
- `pyproject.toml` 定义 Python 包的元数据；
- `ezkl.pyi` 是类型提示文件，能看到所有可调用的函数。

**一个坑**：`pip install ezkl` 只装 Python 绑定，**不含 CLI 二进制**。要用命令行得单独下 release 的 `ezkl.exe`。

## 六、一个容易忽略的细节

pyo3 调用有 GIL（全局解释器锁）的问题。

如果你的服务是多线程 Python，多个 `verify` 调用会**串行**执行（因为 GIL）。解决办法：

- 用 `pyo3::allow_threads` 释放 GIL（EZKL 部分函数做了）；
- 或者用多进程（每个进程一个解释器）；
- 或者干脆用 Rust 写服务，Python 只做胶水。

## 七、自检答案

> 问：说清「为什么交付要给常驻服务而不是命令行」。

答：因为 CLI 每次调用都要付启动成本（加载 33 MB 二进制、反序列化 vk、初始化运行时），约 300 ms，而纯验证只要 40–60 ms。常驻服务把这部分成本摊到启动时一次，之后每次请求只做验证，单次稳定在 50 ms，吞吐提升 6–8 倍。对「1 秒指标」来说，这是决定性的差别。

## 八、一句话记住

**70 毫秒里只有 3 毫秒在验证，剩下全是启动和读 SRS。要指标，先看这条分布；要吞吐，才做常驻服务。**
