# witness泄露

> **支撑** ｜ 前置：05_zkML层/04_语义边界/02_五种可见性

**一句话**：协议本身不泄露 witness，但 witness.json 是硬盘上的一个文件。谁能读到它，谁就直接看见了全部输入和权重。

**在 EZKL 里的落点**：gen-witness 的输出；只能靠文件权限、传输加密、临时目录清理，不靠密码学。

## 一、一个矛盾的事实

你的系统可能这样宣传：

> 采用零知识证明，验证方无法获知模型的权重和用户的输入。

这句话在**协议层面**是对的。

但跑完 `prove` 之后，你的工作目录里躺着一个 `witness.json`，里面是：

- **全部输入**（本项目 28×28 的图，784 个定点数，还原后就是原图）；
- **全部输出**；
- **权重**（当 `param_visibility` 是 `private` 或 `hashed` 时，会出现在 `processed_params` 字段里；设成 `fixed` 时权重进了电路常量，这个字段是空的）。

**没有中间层激活值** —— 这一点和我原来的写法不同，是实测纠正的：`prove` 时电路会按输入重新算一遍，中间值只在内存里存在。但输入和权重已经足够致命了。

**谁能读到这个文件，谁就直接看见了所有秘密。** 不需要破解任何密码学。

## 二、三条泄露路径

**路径一：磁盘**

- 文件留在工作目录；
- 被打进 Docker 镜像；
- 被 `git add .` 提交（真实发生过很多次）；
- 落在 `/tmp` 或共享目录。

**路径二：日志**

- 调试时 `print(witness)`；
- 异常堆栈里带上了张量内容；
- 监控系统采集了标准输出。

**路径三：传输**

- 把 witness 发给「帮忙排查」的同事；
- 通过未加密的 HTTP 传给证明服务；
- 云函数的临时存储没设权限。

## 三、防御：四条，按优先级

**第一，用完即删。**

```
prove 成功 → 立刻删 witness.json
```

如果流程需要保留（比如要重跑），至少加密存储，并设过期时间。

**第二，权限收紧。**

文件权限 600，目录不放共享盘，容器里用非 root 用户。

**第三，传输加密。**

如果证明服务和验证方分离，witness 只能走内网 + TLS，绝不走公网。

**第四，别打日志。**

生产环境关掉 debug 级别的张量打印；异常处理里不要 `{:?}` 整个张量。

## 四、一个容易忽略的场景

**云函数 / Serverless。**

很多 zkML 部署方案是「用户上传输入 → 云函数跑 prove → 返回 proof」。

在这种架构里：

- witness 落在云函数的临时文件系统；
- 执行环境可能被复用（冷启动复用）；
- 日志被云厂商采集。

**这是泄露风险最高的一种部署方式。** 如果必须用，至少做到：

- 每次执行用独立临时目录，结束即删；
- 关掉平台的标准输出采集；
- 用内存文件系统（tmpfs）。

## 五、为什么这件事比「可信设置」更值得担心

对比一下风险等级：

| 风险 | 被利用的难度 | 后果 |
|---|---|---|
| 可信设置被攻破 | 极高（要拿到 τ） | 全系统失效 |
| **witness 泄露** | **极低（读个文件）** | **模型和输入全泄露** |

前者是理论风险，后者是运维风险。**现实中后者发生的概率高几个数量级。**

## 六、自检答案

> 问：说清「证明零知识」和「文件没泄露」是两件事，并给出三条防泄露措施。

答：零知识是协议性质——proof 不泄露 witness；但 witness 本身是硬盘上的文件，与协议无关。三条措施：一是 prove 后立即删除 witness.json（或加密存储并设过期）；二是收紧文件权限、不放共享目录、容器内用非 root；三是关闭生产环境的张量级日志、witness 传输只走内网加密通道。

## 七、一句话记住

**proof 是零知识的，witness.json 不是。加密学管协议，管不了 `ls`。**
