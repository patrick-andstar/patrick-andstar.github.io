## 一、ONNX 是什么

不是框架，是**交换格式**。

PyTorch 训完，导成一个 `.onnx` 文件。这个文件里只有三样东西：

1. **计算图**：一串节点，每个节点写清「用什么算子、吃哪几个张量、吐哪个张量」；
2. **权重**：所有参数的具体数值（存在 `initializer` 里）；
3. **形状信息**：每个张量的维度。

没有 Python 代码、没有训练逻辑、没有优化器状态。**就是一个静态的计算清单。**

## 二、文件里到底有什么

一个 ONNX 图，结构大致是：

```
graph
├── input:  "input_1"  shape=[1,3,224,224]  dtype=float32
├── initializer: "conv1.weight" [64,3,7,7]  ← 权重就在这
├── node 0: Conv(input_1, conv1.weight) -> conv1_out
├── node 1: Relu(conv1_out) -> relu1_out
├── node 2: MaxPool(relu1_out) -> pool1_out
├── ...
└── output: "output_1"  shape=[1,1000]
```

`ezkl table` 干的就是把这个结构打印成一张表，让你看每个算子支不支持。

## 三、为什么 ZK 喜欢静态图

因为电路要求**形状和拓扑在编译期完全确定**。

- 静态图：每一层的输入输出形状都写死 → 可以算出要多少行；
- 动态图（比如 PyTorch 的 eager 模式）：形状可以运行时变 → 电路没法编。

所以 ONNX 这种「先冻结再执行」的模型，天生适合 ZK。反过来说，**任何带动态控制流的模型（if/while、动态 shape）都进不了电路**。

这也是为什么 Transformer 类模型比 CNN 难做：注意力里的 softmax、可变序列长度，都会引入动态性。

## 四、权重存在哪，很关键

ONNX 把权重和结构放在**同一个文件**里。

这在普通推理里很方便（一个文件搞定），但在 ZK 里带来一个必须处理的问题：**权重是数据，不是结构。**

于是 EZKL 在 `gen-settings` 时问你：这些权重，你想当结构（`fixed`）还是当数据（`private`）？

- 当结构：编译进电路，vk 绑定，换权重就得重建（`04/03/05`）；
- 当数据：走 witness，vk 只绑结构，可以换。

**ONNX 不区分这两者，是 EZKL 替你做了这个决定。**

## 五、一个实践中的坑

ONNX 有多个「opset 版本」。不同版本的算子定义略有差异，老版本导出的模型在新工具链上可能读不出来。

EZKL 用 `tract` 解析，对 opset 的支持有范围。遇到「算子不支持」，先查两件事：

1. 算子本身在不在 `LookupOp` / `circuit/ops` 的支持列表里；
2. opset 版本是不是太新或太旧。

**经验**：导出时显式指定 opset（比如 13 或 17），别用默认的最新版。

## 六、自检答案

> 问：说清 ONNX 里权重存在哪、算子怎么描述、为什么换框架还能读。

答：权重存在 `initializer` 里，是一组命名的张量；算子描述在 `node` 里，每个节点有 `op_type`、输入输出名和一个属性表（比如卷积的 kernel_shape、strides）。因为 ONNX 定义的是「算子的语义 + 图的连接关系」，与训练框架无关，所以 PyTorch 导出的模型可以被 ONNX Runtime、tract、EZKL 等不同后端读取。

## 七、一句话记住

**ONNX 是静态的算子清单 + 权重文件。静态是优点（能进电路），也是限制（动态模型进不来）。**
