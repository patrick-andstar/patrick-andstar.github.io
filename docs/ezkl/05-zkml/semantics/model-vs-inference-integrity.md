# 模型完整性vs推理完整性

> **核心** ｜ 前置：05_zkML层/04_语义边界/02_五种可见性

**一句话**：哈希/签名只能证「文件没变」；ZK 才能证「用的就是这份权重，而且算对了」。两者缺一个都会漏。

**在 EZKL 里的落点**：与 LightVeriFL 的分工口径；EZKL 的 param_visibility。

## 一、两个词，四个字，完全不同的东西

| | 模型完整性 | 推理完整性 |
|---|---|---|
| 问的是 | 这个模型**文件**被改过吗 | 这次**计算**按这个模型跑了吗 |
| 防的是 | 掉包（换成别的权重） | 偷工（换一套逻辑算） |
| 用什么 | 哈希 / 签名 | 零知识证明 |
| 成本 | 毫秒级 | 秒级证明、毫秒级验证 |
| 能不能互相替代 | **不能** | **不能** |

## 二、为什么哈希不够

哈希能证明「文件没变」。但它防不住这件事：

> 服务方拿着正确的模型文件，实际却用另一套代码算，然后声称「我按这个模型算的」。

文件哈希照样对得上，因为文件确实没动。**问题出在「执行」这一步，不在「文件」这一步。**

这就是 ZK 的独占价值：它证的不是「我有什么」，是「我做了什么」。

## 三、为什么 ZK 也不够

ZK 证「电路 C 执行正确」。但 C 是什么？

- 如果 C 里没有绑定权重（`param_visibility=private`），那 C 只代表「结构」；
- 攻击者换一版权重，C 不变，证明照样有效。

所以 ZK 单独也保证不了「用的是这份权重」。要么：

- 用 `fixed`（把权重焊进电路，vk 绑定）；
- 要么把权重的哈希作为公开输入（承诺化）。

## 四、两者怎么咬合（关键）

这是你项目里最值得写清楚的一段。假设场景是联邦学习：

```
第 t 轮：
  1. 各参与方上传更新 → 聚合方算出全局模型 W_t
  2. 计算 h_t = H(W_t)          ← 哈希（LightVeriFL 那套）
  3. 用 W_t 做推理，生成证明 π
  4. π 的公开输入里包含 h_t      ← 咬合点
  5. 验证方检查：verify(π) 且 h_t 等于本轮聚合结果的哈希
```

**没有第 4 步，两套机制只是并列，不是咬合。**

有了它，验证方能确认：这次推理用的权重，就是本轮刚聚合出来的那一版。

## 五、一个必须承认的弱点

哈希是「事后比对」，不是「事前绑定」。

也就是说：如果攻击者在生成证明之前就把 `h_t` 换成了别的值（比如用了旧模型但声称是新模型），验证方只能发现「哈希对不上」，但**无法证明「哪个才是真的」**。

所以哈希的来源必须可信：

- 聚合方签名；
- 或者哈希本身进链/进日志；
- 或者多方交叉确认。

**这是这套方案唯一的信任锚点**，写方案时要单独说明。

## 六、一张对照表（可直接放进报告）

| 需求 | 机制 | 覆盖 | 不覆盖 |
|---|---|---|---|
| 模型文件没被改 | SHA256 + 签名 | 文件字节级 | 执行过程 |
| 推理按声明模型执行 | ZK（任何 param_visibility） | 电路层执行 | 用的是哪份权重 |
| 用的是本轮全局模型 | 权重哈希作公开输入 | 权重版本 | 聚合过程本身 |
| 聚合结果正确 | LightVeriFL 类方案 | 聚合计算 | 推理过程 |
| 输出数值可接受 | 容差检查（`05/03/04`） | 端到端误差 | 模型准确率 |

五条需求，五个机制，**没有一个能兼任两个**。

## 七、自检答案

> 问：说清「两者缺一个会漏什么」，并给出各自该用哪种机制。

答：只有哈希没有 ZK，会漏「换一套逻辑算但文件没变」——执行过程无人担保；只有 ZK 没有哈希，会漏「用的是哪一版权重」——尤其当 `param_visibility=private` 时，vk 只绑结构。所以模型完整性用哈希/签名（快、字节级），推理完整性用 ZK（慢、执行级），两者用一个「权重哈希作为公开输入」的动作咬合起来。

## 八、一句话记住

**哈希管「我有什么」，ZK 管「我做了什么」。中间用权重哈希把两者焊上，缺一环就漏一环。**
