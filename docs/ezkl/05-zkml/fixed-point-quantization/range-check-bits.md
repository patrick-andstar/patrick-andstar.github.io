# 范围检查与bits

> **核心** ｜ 前置：05_zkML层/02_定点量化/03_溢出为何仍能出合法证明

**一句话**：每个中间值都要证明落在 [−2^b, 2^b)；没有范围检查，溢出就无法被发现。

**打个比方**：光记账不够，还得规定「每个格子只能写 8 位数」。不规定，溢出就永远查不出来。

**在 EZKL 里的落点**：GraphSettings.required_range_checks；RANGE_MULTIPLIER。

## 一、问题的根源

回忆 `01/01/01` 的结论：**有限域里没有「大小」**。

在 mod p 里，5 和 p−5 是「同一个数的不同代表」，你没法说哪个更大。所以：

- 电路不知道 127 < 128；
- 电路也不知道某个值「溢出了」；
- 电路甚至不知道一个数是正还是负。

那怎么表达「这个值必须在 ±2¹⁵ 之间」？

## 二、两条路

**路线 A：拆位（bit decomposition）**

把一个数拆成 b 个二进制位，每位单独约束「必须是 0 或 1」，再把这些位重新组合成原数。

> v = b₀ + 2b₁ + 4b₂ + … + 2^(b−1)·b_(b−1)，每个 bᵢ ∈ {0,1}

代价：b 条布尔约束 + 一次线性组合。b = 16 就是 16 条约束，很贵。

**路线 B：查表（lookup range check）**

预先做一张表，里面有 0 到 2^b−1 全部的值。然后证明「我的值在这张表里」。

> 「v 在表里」 ⟺ 「0 ≤ v < 2^b」

代价：一次成员查询（`03/03/01`）。比拆位便宜得多，这是现代 zk 系统的标准做法。

**EZKL 用的是路线 B**：`settings.json` 里的 `required_range_checks` 就是「要对哪些区间做检查」。

## 三、bits 到底是什么（以及一个必须纠正的说法）

先说一个事实，免得你拿着这个概念去 `settings.json` 里找参数却找不到：

> **EZKL 的设置里没有叫 `bits` 的字段。** 有的是 `lookup_range`（`-B`，一对整数，默认 `[-32768, 32768]`）、`decomp_base` / `decomp_legs`（数分解的基与段数），以及 `logrows`。

`bits` 是我们**口头上的对数说法**：一个宽度为 W 的表，习惯说成「bits = log₂W」。默认的 `lookup_range` 宽 65536 = 2¹⁶，口语就说「16 位表」。本讲义沿用这个说法，但你要知道它不是参数名。

概念上，它有两个容易混的含义：

| 场景 | 「bits」指什么 | 影响 | EZKL 里对应 |
|---|---|---|---|
| **量化位宽** | 每个数值用多少位表示 | 范围 ±2^(bits−1)，精度 | 由 `scale` 与 `lookup_range` 共同决定 |
| **查找表宽度** | 表有多少档（2^bits） | 表占多少行，函数逼近精度 | `lookup_range` |

两者常常取同一个值，但不是一回事。前者决定「数值能不能装下」，后者决定「函数逼近得多准」。

配错的表现也不同：

- 量化位宽太小 → 中间值饱和（`05/02/03`）；
- 查找表太窄 → sigmoid 误差大，甚至查不到表（超出范围直接失败）。

## 四、负数怎么处理

域里没有负数，所以用「加偏移」：

> 真实值 −3，在 b = 8 的表示里存成 256 − 3 = 253

然后范围检查的对象是「253 在 0..255 里」。要判断符号时，再看它是否 ≥ 128。

**这就是为什么电路里的「负数」看起来都是巨大的正整数**（`01/01/01` 提过）。你在调试 witness 时看到 `p - 3` 这样的值，不要惊讶。

## 五、代价：每个中间值都要检查

范围检查不是免费的：

- 每个中间张量的每个元素，都要做一次（或几次）检查；
- 检查会占行、占查找表配额；
- 层数越深、张量越大，检查次数越多。

本项目实测里，一个 3 万多行的小模型，范围检查占了相当比例的行数。**这也是为什么「bits 调大」不只是精度问题，还是行数问题**（`03/03/05`）。

## 六、在 EZKL 里

- `GraphSettings.required_range_checks`：一张清单，列出要对哪些区间做检查；
- `RANGE_MULTIPLIER = 2`：表范围要留 2 倍安全系数（`src/circuit/table.rs`）；
- 相关参数在 `settings.json` 里，`gen-settings` 会根据量化参数自动填。

## 七、自检答案

> 问：说清「range check 与 lookup 是什么关系」。

答：range check 是目标（证明某个值落在 [0, 2^b) 内），lookup 是实现手段（把 0..2^b−1 做成一张表，证明该值在表里）。用 lookup 做 range check 比拆位便宜得多：拆位要 b 条布尔约束，查表只要一次成员查询加表本身的开销。所以现代 zk 系统（包括 EZKL）都用查表来做范围检查。

## 八、一句话记住

**域里没有大小，所以「在范围内」只能靠查表证明。每个中间值都要查一次，这就是成本。**
