# BN254与BLS12-381的选型

> **核心** ｜ 前置：01_数学地基/03_椭圆曲线/02_标量乘法与离散对数

**一句话**：选 BN254 不是为了更安全，而是因为 EVM 的 ecPairing 只认它。安全等级约 100 bit。

**在 EZKL 里的落点**：Cargo.toml 里 halo2curves 固定走 bn256。

## 一、两条曲线，都够用

做 KZG 需要「配对友好」的曲线，主流只有两条：

| | BN254（alt_bn128） | BLS12-381 |
|---|---|---|
| 域大小 | 约 254 位 | 约 381 位 |
| 安全等级 | **约 100 bit** | **约 128 bit** |
| 配对效率 | 高 | 略低 |
| 以太坊 | **EVM 有原生预编译**（0x06 / 0x07 / 0x08） | 没有原生预编译（EIP-2537 长期提案中） |
| 典型用户 | EZKL、早期 zkRollup | 以太坊共识层、Filecoin |

两条都能做 KZG，都能跑 Halo2。**差别不在「能不能」，在「链上验贵不贵」。**

## 二、为什么 EZKL 选了 BN254

两个原因叠加：

1. **halo2 生态早期就选了它**。zkonduit 的 fork 直接锁 `bn256`，改曲线等于把整条工具链（SRS 格式、验证器、Solidity 模板）全部重做。
2. **EVM 兼容**。合约里调 `ecPairing` 预编译，几万 gas 就能验一次；换成 BLS12-381，得用纯 Solidity 实现的配对，gas 高一个数量级。

所以这是一个**被生态绑死的选择**，不是「经过比较后最优」。理解了这一点，你就明白为什么改不动。

## 三、「254 位曲线」不等于「254 位安全」

这是最容易被误读的地方。

- 曲线的域是 254 位，但**攻击者不需要穷举 2²⁵⁴**；
- 破解有限域离散对数用的是**数域筛法（NFS）**，复杂度是亚指数的；
- 对 254 位素域的估计约 **2¹⁰⁰** 次操作。

所以正确说法是「约 100 bit 安全」，不是「254 bit 安全」。

100 bit 是什么概念：不算「现在就能破」，但离 80 bit 的工程底线只剩一档余量。NIST 的建议是 112 bit 起步、128 bit 主流。

**写报告时的口径**：如果写「本系统提供 128 bit 安全」，那是错的；要么写「依赖 BN254，约 100 bit」，要么写「与主流 zkEVM 同一安全档位」。别含糊过去。

## 四、这个选择在 EZKL 里留下的痕迹

- `Cargo.toml` 里 `halo2curves` 锁死 `bn256`；
- SRS 文件里**每个幂次 128 字节**（单项式基与拉格朗日基各 64 字节，未压缩）；而证明里的一个点压缩后是 32 字节 + 1 字节前缀；
- `proof.json` 的 `hex_proof` 是一整段字节块，里面编码着一串压缩点（每个 33 字节）；
- vk 里有配对所需的 G2 点（G2 在扩域上，所以是 64 字节一组）。

一个具体的算术：`logrows = 16` 时 SRS 要 2¹⁶ 个点，约 8.4 MB —— 正好对上本项目里 `kzg16.srs` 的大小。你可以拿这个反推任何 k 的 SRS 体积。

## 五、如果以后要换曲线

换 BLS12-381 意味着：换 SRS、换曲线库、换证明序列化、换验证器、重跑所有 setup。**已有 vk 全部作废。**

所以现实中的做法不是换，而是**接受 100 bit，在报告里说清楚**。这也是一种诚实：不把数字讲漂亮。

## 六、自检答案

> 问：解释「EZKL 为什么绑死 BN254」，并说出这个选择的代价。

答：因为 halo2 生态（zkonduit fork、halo2curves、snark-verifier、Solidity 验证器）全部围绕 bn256 构建，且 EVM 有原生 ecPairing 预编译，链上验证成本低。代价是安全等级只有约 100 bit，比 BLS12-381 的约 128 bit 低一档；且换曲线等于整条工具链重做、所有 vk 作废。

## 七、一句话记住

**不是选最好的曲线，是选生态锁死的那条。254 位域 = 100 bit 安全，别写成 128。**
