# 点的表示与压缩序列化

> **支撑** ｜ 前置：01_数学地基/03_椭圆曲线/02_标量乘法与离散对数

**一句话**：proof.json 里那些 0x… 是压缩后的 G1 点：只存 x 和一个符号位，y 由曲线方程解出。

**打个比方**：曲线是上下对称的，知道 x 坐标，再记一个「在上半边还是下半边」，点就唯一确定了——所以 33 字节就够。

**在 EZKL 里的落点**：src/pfsys 与 eth.rs 的序列化；格式错一个字节，verify 直接 false。

> 读完约 7 分钟。这一篇解释 `proof.json` 里那段 `0x` 长串到底是什么。

## 一、一个点原本要存什么

曲线上的点是 (x, y)，两个坐标。

BN254 的域是 254 位，一个坐标要 32 字节。所以未压缩的点是 **64 字节**。

但 `proof.json` 里的点只有 33 字节。为什么？

## 二、压缩：y 可以算出来

曲线方程是：

> y² = x³ + 3

给定 x，右边是一个确定的数。要求 y，就是**在有限域里开平方**。

一个平方根方程 `y² = c` 在素域里恰好有 0 个或 2 个解（如果 c 是二次剩余就是 2 个，否则 0 个），而且两个解互为相反数：

> y 和 p − y

所以：**知道 x，y 只有两个候选，且它们一奇一偶。**

于是只需要存：

- 32 字节的 x；
- 1 个比特，说明 y 是奇数还是偶数。

**总共 33 字节。** 前缀 `0x02` 表示 y 为偶，`0x03` 表示 y 为奇。

## 三、解压要做什么

1. 算 `c = x³ + 3 mod p`；
2. 判断 c 是不是二次剩余（用欧拉准则：`c^((p−1)/2) ≡ 1` 则是）；
3. 用 Tonelli-Shanks 算法求一个平方根 y₀；
4. 另一个根是 `p − y₀`；
5. 选那个奇偶性与前缀一致的。

**第 2 步是关键**：如果 c 不是二次剩余，说明这个 x 根本不在曲线上 —— 解码直接失败。

## 四、这正是「篡改一个字节就失败」的原因

你手改 `proof.json` 里的一个字节：

- 如果改的是前缀（0x02 → 0x03），解出来的 y 会变成另一个根，这个点可能仍在曲线上，但和原来的点不同 → 承诺对不上 → 验证失败；
- 如果改的是 x，那 `x³ + 3` 大概率不是二次剩余 → 解码直接报错；
- 如果运气极好，新 x 也在曲线上，那也只是「换了一个点」，验证照样失败。

**所以「改一个字节必失败」不是巧合，是三层检查叠加的结果**（前缀、在曲线上、承诺匹配）。

## 五、G2 为什么是 64 字节

G2 的点坐标不在 Fq，而在扩域 Fq² 上。

一个 Fq² 元素 = 两个 Fq 元素 = 64 字节。所以 G2 的压缩点是：

- 64 字节的 x（两个分量）；
- 1 字节前缀。

共 65 字节，未压缩是 128 字节。

这就是为什么 `vk.key` 比同样点数的 G1 数据大一倍。

## 六、在 EZKL 里

- `src/pfsys` 负责点的序列化/反序列化；
- `proof.json` 里的 `hex_proof` 是一整段十六进制字节块（本项目 3,072 字节 = 6,146 个字符），里面**按顺序**编码着一串压缩点与求值，不是一个点，也不是给人读的字段；
- 「点不在曲线上」是 verify 失败的第二大原因（第一是约束不满足）。

## 七、自检答案

> 问：说清「压缩点为什么只需 32 字节 x 加 1 位符号」，以及篡改一个字节会怎么失败。

答：因为曲线方程给定 x 后 y² 是确定的，而 y 只有两个互为相反数的解，一奇一偶，所以只需 1 个比特区分。篡改时：改前缀会解出另一个根、点变了导致承诺不匹配；改 x 大概率使右边不是二次剩余，直接解码失败；即使恰好仍在曲线上，也是一个不同的点，同样验不过。

## 八、一句话记住

**y 能由 x 算出来，两个解一奇一偶，所以 33 字节就够。改一个字节，三层检查全在等你。**
