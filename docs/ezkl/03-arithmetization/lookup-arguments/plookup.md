# Plookup原理

> **支撑** ｜ 前置：03_算术化/03_查找表/01_为什么需要查找表、03_算术化/02_PLONKish/03_复制约束与置换论证

**一句话**：把「值在表里」化成两个多重集的并集相等，再用排序或累积和把并集证明压成一个等式。

**打个比方**：证明「我手里的牌都出自这一副」，最省的办法是两堆都排好序，看能不能一一对上。

**在 EZKL 里的落点**：halo2 的 lookup argument 基础。

    说清「并集论证」为什么能证明成员关系。

> 读完约 8 分钟。这一篇讲第一代查表论证的思路，理解它才能看懂 LogUp 改进了什么。

## 一、目标

给定两列数：

- **f**（查询列）：这次计算里用到的输入，比如 256 个 sigmoid 的输入；
- **t**（表列）：预先算好的表，比如 256 个档位。

要证明：**f 里的每个元素都在 t 里出现过。**

这是「成员关系」，不是「相等」。

## 二、核心技巧：排序合并

如果两堆数都排好序，判断「f ⊆ t」就变成扫一遍的事。

但电路里排序很贵。Plookup 的巧妙之处是：**不真排序，而是证明「存在一个排好序的合并序列」。**

具体构造：

1. 把 t 的元素（按顺序）和 f 的元素交错排成一个新序列 s；
2. 要求 s 满足两条：
   - s 是「t 的重复」—— 每个 t 的元素在 s 里连续出现若干次；
   - f 的每个元素都出现在 s 里，且位置正确。

然后证明「s 是 t 的一个合法扩展，且包含 f 的全部元素」。

## 三、怎么用连乘证明

回忆复制约束（`03/02/03`）：用 grand product 证明「两堆值互为排列」。

Plookup 本质上要证两件事：

1. **s 是 t 的合法扩展**（s 里的值都来自 t，且按 t 的顺序出现）；
2. **f 按顺序嵌在 s 里**（每个 f 的元素都能在 s 的对应位置找到）。

这两件事都可以写成「两个多重集相同」，于是用同一个工具——随机加权连乘——来压：

> ∏(左侧值 + β) = ∏(右侧值 + β)

实现上通常用**一个**累积乘积多项式（grand product）配合首尾边界条件把两件事合并处理，而不是真的写两个独立等式。这里为了讲清楚才拆成两步。

## 四、直觉版

想象两副牌：

- 桌上摊着一副标准牌（t）；
- 你手里有一把牌（f）；
- 你要证明「我这些牌都是从桌上那副里抽的」。

办法：把两堆牌**按同样顺序排好**，然后逐张对照 —— 你手里的每一张，都能在桌上那副里找到对应位置。

Plookup 的「排序合并」就是让这个对照可以在电路里用一个连乘完成，而不需要真的做排序网络。

## 五、代价与局限

| 项 | 说明 |
|---|---|
| 证明开销 | 两次 grand product，各占一列 |
| 预处理 | 需要构造 s 的排列，编译期算好 |
| 局限 | 只支持「单列查单列」；多列要拆成多次 |
| 局限 | 表必须是固定的（不能是 witness） |

最后两条正是 LogUp 和 mv-lookup 要解决的（`03/03/03`、`03/03/04`）。

## 六、在 EZKL 里

- halo2 的 lookup 模块实现了 Plookup 的变体；
- EZKL 的非线性算子（`LookupOp::Sigmoid` 等）走这条路；
- `settings.json` 里的 `required_lookups` 决定要生成哪些表。

**注意**：Plookup 的表是**固定**的（编译期定），所以「动态表」需要另一种论证 —— 这就是 EZKL fork 里 `mv-lookup` 特性的由来。

## 七、自检答案

> 问：说清「并集论证」为什么能证明成员关系。

答：因为「f 的每个元素都在 t 里」等价于「存在一个序列 s，它既是 t 的合法扩展，又包含 f 的全部元素」。而「两个序列是同一个多重集」可以用一个随机加权的连乘等式来验证（顺序无关）。于是成员关系被转成两个可验证的连乘等式，不需要真的排序，也不需要逐元素比较。

## 八、一句话记住

**不排序，只证明「存在一个排好序的合并序列」。两个连乘，替掉一次排序。**
