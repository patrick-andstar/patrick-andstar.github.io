# 动态查找与向量查找

> **选读** ｜ 前置：03_算术化/03_查找表/03_LogUp与对数导数

**一句话**：表本身也可以是 witness（任意张量），而且一次能查多列——EZKL 的非线性算子和 einsum 都靠这个。

**打个比方**：静态表是「印好的菜单」，动态表是「现场写的菜单」；后者能一次查一整行，灵活但要多花约束。

**在 EZKL 里的落点**：Cargo.toml 的 features = ["mv-lookup"]；GraphSettings.dynamic_lookup_params。

## 一、静态表的局限

标准 halo2 的查找表是**固定**的：

- 表内容在编译期确定；
- 存在 fixed 列里；
- 由 vk 绑定。

这对 sigmoid 这类「函数表」够用。但对 zkML 有两类场景不够：

**场景一：表本身是数据。**
比如 attention 里的 key/value 矩阵，它们不是「预定义的函数」，而是这次推理的具体数值。

**场景二：一次要查多列。**
一个张量运算往往是「(a,b,c) → (x,y)」，输入输出都是多维的。单列查找要拆成多次。

## 二、动态表

**动态表**允许表的内容来自 witness（advice 列），而不是 fixed 列。

于是：

- 表可以是任意张量（这次推理的中间结果）；
- 但仍然要证明「查询确实落在这张表里」。

代价：

- 表不再是常量 → 不能预先算进 vk；
- 查找论证要同时处理「两个 witness 列集合的包含关系」，比静态表复杂。

## 三、向量查找（mv-lookup）

标准查找是「一个值在一个表里」。

**mv-lookup**（multi-value lookup）是「一个元组在表的某一行里」：

> (a, b) ∈ {(t₁ᵢ, t₂ᵢ)}

也就是**一次查多列**。

在 zkML 里这非常有用：

- einsum 的输入输出对；
- 非线性算子的（输入，输出）对；
- 甚至整个张量的形状映射。

## 四、EZKL 怎么用

`Cargo.toml` 里：

```toml
halo2_proofs = { features = ["circuit-params", "mv-lookup"] }
```

两个特性：

- `mv-lookup`：向量查找；
- `circuit-params`：允许运行时传电路参数（模型规模是动态的，标准 halo2 要求编译期常量）。

另外 `halo2_wrong_ecc` 也钉在 `ac/chunked-mv-lookup` 这个分支上，说明整套 fork 是围绕同一个查找扩展做的；不过 EZKL 的 `src/` 里并没有直接调用它（只是 `snark-verifier` 的传递依赖），别把它的存在当成「EZKL 在电路里做曲线运算」的证据。

`GraphSettings` 里有对应的字段：

- `dynamic_lookup_params`（总列数、最大输入长度、查找次数）；
- `einsum_params`（张量收缩的维度信息）。

**这些字段存在，说明编译期就在为动态查找做预算。**

## 五、代价

| 项 | 影响 |
|---|---|
| 证明时间 | 动态表的查找论证更重 |
| 行数 | 表本身占 witness 空间 |
| 实现复杂度 | 需要非标准 halo2（换不回 upstream） |
| 审计覆盖 | 这部分是 fork 独有，审计范围要考虑 |

最后一条值得注意：**标准 halo2 的审计结论不完全覆盖 fork 的扩展**。

## 六、一个判断

如果你的模型只有 ReLU + Conv + FC（没有 sigmoid/softmax/layernorm），那动态查找用得很少，标准 halo2 就够。

但只要有 LayerNorm 或 Softmax，就必然会用到查表，也就会碰到这些扩展。

**这也是为什么 EZKL 不能简单换回 upstream halo2** —— 它的算子实现依赖这些扩展。

## 七、自检答案

> 问：说清「静态表」与「动态表」在电路里差在哪、各自适合什么场景。

答：静态表的内容在编译期固定、存在 fixed 列、由 vk 绑定，适合「预定义函数」（sigmoid、sqrt 等）；动态表的内容来自 witness（advice 列），可以是这次推理的任意张量，适合「表本身是数据」的场景（attention 的 KV、einsum 的映射）。代价是动态表不能预计算进 vk，查找论证更复杂、更慢。

## 八、一句话记住

**静态表是印好的菜单，动态表是现场写的菜单。EZKL 两种都要，所以改了 halo2。**
