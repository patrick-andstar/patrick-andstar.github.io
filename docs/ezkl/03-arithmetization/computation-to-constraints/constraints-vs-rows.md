# 约束数与行数

> **核心** ｜ 前置：03_算术化/01_从计算到约束/01_电路抽象与witness

**一句话**：约束条数决定电路逻辑对不对，行数决定证明要多久、内存要多少。两者不是一回事。

**在 EZKL 里的落点**：GraphSettings 里的 num_rows 与 total_assignments。

!!! question "自检（能答上来就算过）"
    解释「加了一条约束但行数没变」为什么是可能的。

---

> 读完约 7 分钟。这一篇解释一个常年被混淆的区别，也是估算成本的第一步。

## 一、两个数字，不是一回事

| | 约束（constraint） | 行（row） |
|---|---|---|
| 是什么 | 一条必须成立的等式 | 表格里的一格高度 |
| 决定什么 | 逻辑对不对 | 证明要多久、内存要多少 |
| 谁关心 | 电路设计者 | 算预算的人 |

举个例子：一个门里可以塞 `a·b + c − d = 0` 这一条约束，它同时管了乘、加、减三件事 —— **一条约束，一行**。

但如果我想加一条「a 必须小于 2¹⁶」，那是另一条约束，通常还要占额外的行（因为范围检查要靠查找表，`05/02/04`）。

所以：**约束多了，行不一定等量增加；行数才是钱。**

## 二、行数必须是 2 的幂

因为在单位根上做插值和 NTT（`01/04/01`、`01/04/02`），域的大小必须是 2 的幂。

`logrows = 16` → 65536 行，`logrows = 17` → 131072 行。只能翻倍。

这带来一个残酷的台阶效应：**多一行装不下，就得多付一倍的钱。**

## 三、行数是怎么估出来的

EZKL 的 `gen-settings` 会做一遍「纸上推演」：遍历 ONNX 图的每个算子，累加它需要的行数，再加上盲化行（blinding rows）和查找表的预留，向上取到 2 的幂。

本项目实测的几个点：

| 模型 | num_rows | logrows | 说明 |
|---|---|---|---|
| `3l_relu_conv_fc` | 36,428 | 16 | 小 demo，17 秒跑完 |
| 缩小 ResNet（32×32, w=0.25） | 11,285,288 | 24 | 21 秒 |
| 缩小 ResNet（64×64, w=0.25） | 34,085,192 | 26 | 70 秒，公开 SRS 上限 |
| 完整 ResNet50 | 约 1.6–2.0 G | 31 | 无法进行 |

注意 36,428 离 65,536 还有余量，但 k 已经是 16 了 —— 因为向上取整。

## 四、成本怎么随行数走

本项目实测的线性系数（32 线程 CPU）：

| 指标 | 每行 |
|---|---|
| 证明时间 | ≈ 40 微秒 |
| setup 时间 | ≈ 56 微秒 |
| `pk` 大小 | ≈ 4.3 KB |
| 峰值内存 | ≈ 9–11 KB |
| SRS 大小 | 128 字节（文件里每幂次存两种基、各 64 字节） |

拿 36428 行套一下：prove ≈ 1.5 秒（实测 2.9–4.2 秒，因为还有固定开销），pk ≈ 157 MB（实测 265 MB，同样是取整到 2¹⁶ 的原因）。

**估算时要用 2^k 而不是实际行数** —— 因为电路是按 2^k 分配的。

## 五、最容易犯的错

**错误一：以为「约束越少越快」。**
不一定。约束少但行多（比如大量范围检查），照样慢。

**错误二：用实际行数估成本。**
要用 2^k。36428 行按 65536 算，差近一倍。

**错误三：以为加一层网络只加一点。**
加一层可能让总行数跨过 2 的幂的台阶，成本直接翻倍。这就是为什么「小改一版模型」有时会让证明时间从 3 秒变 6 秒。

## 六、自检答案

> 问：解释「加了一条约束但行数没变」为什么是可能的。

答：因为一条行内可以放多条约束。比如一个自定义门里可以同时约束 `a·b = c` 和 `c + d = e`，两件事共用一行，行数不变而约束数 +1。只有当新增的逻辑需要新的单元格（新的中间变量、新的范围检查、新的查找）时，行数才会涨。

## 七、一句话记住

**约束决定「对不对」，行数决定「贵不贵」。估成本时永远用 2^k，不用实际行数。**
