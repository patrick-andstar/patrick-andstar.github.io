## 一、回一遍直觉

交互式协议里，验证者临场出一个随机数当挑战。非交互版本里，这个随机数改成：

> 挑战 = H(此前所有消息)

一句话就完了。但真正写代码时，问题全在细节里：**「此前所有消息」到底是哪些？按什么顺序？怎么拼？**

答案是一个叫 transcript 的结构。

## 二、transcript 怎么工作

它像一个只能往后追加的账本，有两个动作：

| 动作 | 做什么 | 什么时候用 |
|---|---|---|
| `absorb(msg)` | 把一条消息写进账本 | 每产生一条消息 |
| `squeeze()` | 从账本算出一个挑战 | 需要随机数时 |

关键规则有三条：

1. **顺序不能改。** absorb 的先后就是协议里消息的先后。
2. **squeeze 出来的值也要 absorb 回去。** 否则同一个挑战可以被反复用在不同地方。
3. **每类消息要有「域分离」标签。** 比如 `absorb("commit", C)` 而不是直接 `absorb(C)`。否则一条消息可能被解释成另一种含义。

## 三、为什么第 3 条不是洁癖

想象一个协议里有两种消息：承诺值和公开输入。如果都直接 absorb 原始字节，攻击者可以把「一个很大的公开输入」切成两段，伪装成「两个承诺」，让 transcript 的内容在两种解释下相同。

**这不是假想**。2022 年公开的一类漏洞（被称为 Frozen Heart）就是这样：多个 PlonK 实现因为 transcript 没有正确绑定公开输入或缺少域分离，导致证明可以被伪造。影响面很广，包括一些主流库。

教训很直接：**transcript 的实现细节，就是安全性本身**。它不是「格式问题」。

## 四、在 EZKL / halo2 里

- halo2 有一个 `Transcript` trait，内部维护 sponge 状态；
- 证明生成时，每一批承诺先 absorb，再 squeeze 出一个挑战。halo2 的实际顺序是 **theta → beta → gamma → y → x**（多开点内部再挤 v、u），没有论文里的 α、ζ 这两个名字；
- 验证时**重算一遍同样的 absorb 序列**，所以挑战必须完全一致；
- 任何一处序列化差异（字节序、压缩与否、字段顺序）都会导致挑战不同 → 验证失败。

本项目实测里「改 `proof.json` 任一字段 → `verified: false`」，一半原因在约束不满足，另一半就在挑战对不上。

## 五、一个容易忽略的后果

因为挑战依赖「此前所有消息」，所以**消息的边界必须明确**。

举个反例：如果协议里 absorb 的是两个长度可变的字节串，攻击者可以构造 `("ab", "c")` 和 `("a", "bc")` 得到相同的拼接结果 —— 两种不同的执行，同一个 transcript。

解决办法：长度前缀，或者固定长度编码。这类问题在实现里极其常见，也是最容易被审计漏掉的地方。

## 六、自检答案

> 问：说清「如果攻击者能预测挑战值会发生什么」，并举一个具体作弊方式。

答：如果挑战可预测，证明者就能针对那个特定挑战构造一个「只在该点成立」的假证明。具体做法：先算出挑战 r，再构造一个多项式 P，使它在 r 处等于期望值、在其他地方完全不对——因为验证者只查 r 这一个点（`01/04/03`），假货百分之百通过。这就是为什么挑战必须来自「证明者无法提前控制」的哈希。

## 七、一句话记住

**transcript 不是日志，是安全边界。顺序、标签、长度，错一个就全废。**
