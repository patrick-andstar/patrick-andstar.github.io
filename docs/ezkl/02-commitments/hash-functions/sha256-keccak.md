# SHA256与Keccak

> **支撑** ｜ 前置：02_承诺与哈希/01_哈希函数/01_哈希的三个安全目标

**一句话**：工程里用它们校验 SRS 文件、算模型指纹；电路里几乎不用，因为每一位都要几百条约束。

> 读完约 7 分钟。这一篇讲两种「传统哈希」的结构差异，以及它们在 EZKL 里的两个用处。

## 一、两种结构

| | SHA256 | Keccak（SHA-3） |
|---|---|---|
| 结构 | Merkle–Damgård | Sponge（海绵） |
| 处理方式 | 分块，前一块的输出喂给下一块 | 吸收（absorb）→ 挤出（squeeze） |
| 长度扩展攻击 | **有** | 没有 |
| 电路成本 | 极高 | 极高 |

## 二、Merkle–Damgård 的毛病

SHA256 的流程是：

> h₀ = IV
> hᵢ = compress(hᵢ₋₁, blockᵢ)

问题：**知道 H(m) 之后，可以在不知道 m 的情况下算出 H(m ‖ padding ‖ extra)。**

因为你可以从 h 的最终状态继续往下压。这叫长度扩展攻击。

**这和 ZK 有关系**：如果 transcript 用「简单拼接再哈希」的方式实现，长度扩展就会变成安全问题（`02/01/04` 提过边界不明确的问题）。所以工程上必须用长度前缀或固定编码。

Keccak 的 sponge 结构没有这个毛病：挤出阶段和吸收阶段是分开的，你不能从输出继续「压」。

## 三、为什么电路里几乎不用

因为它们是**按位**设计的：

- 32 位整数的循环移位、按位与、按位异或；
- 64 轮（SHA256）或 24 轮（Keccak），每轮几十个位运算。

在电路里，每个「位」都要占一个域元素，每个位运算都要展开成约束。结果：

> 一次 SHA256 压缩函数 ≈ 几万条约束
> 一次 Poseidon ≈ 几百条

差两个数量级（`02/01/03`）。所以在电路内部做哈希，一律用 Poseidon。

## 四、那 EZKL 里它们还用在哪

两处，都在**电路外**：

**第一，SRS 文件校验。**
`src/srs_sha.rs` 用 SHA256 校验下载的 SRS 没被替换。这一步在普通程序里跑，成本可忽略。

**第二，模型/文件指纹。**
算 ONNX 文件的哈希，用于版本管理、日志、审计。也是电路外。

**规律**：凡是「在电路外做、只需要一次」的哈希，用 SHA256；凡是「要在电路里做」的哈希，用 Poseidon。

## 五、一个容易搞错的地方

「Keccak 比 SHA256 安全」——不严谨。

- 两者都被认为安全；
- SHA256 的碰撞安全是 128 bit（输出 256 位，生日攻击减半）；
- Keccak-256 的碰撞安全也是 128 bit 量级。

差别在结构（sponge vs MD）和抗长度扩展，不在「谁更安全」。

## 六、自检答案

> 问：说清「为什么 SHA256 在电路里贵得离谱」，以及它贵在哪一步。

答：因为 SHA256 完全按位设计：32 位字的循环移位、按位与、按位异或，64 轮迭代。电路里每个比特都要表示成域元素并加布尔约束，每个位运算都要展开成多条约束，于是一次压缩函数要几万条约束，比 Poseidon 贵两个数量级。贵在「把位运算翻译成域运算」这一层，不是算法本身慢。

## 七、一句话记住

**SHA256 在电路外是标配，在电路里是奢侈品。分工：外面用 SHA，里面用 Poseidon。**
